# Autogen benchmark — ground-truth POSITION fix

**Goal:** `autogen-gt-position-fix`. Fix the TypeEvalPy **autogen** benchmark's
ground-truth `(line, col)` generation bug that mis-scores correctly-typed engine
output as `LOCATION_MISS`. This is a **benchmark-corpus** fix: the engine is
already correct (the prior diagnosis proved it — see
[`ENGINE-assignments-location.md`](../../../Archway-worktrees/loop-main-integration/docs/design_notes/ENGINE-assignments-location.md),
verdict (b) unanimous, 0 emission gaps). The corpus ground-truth positions are
wrong; the engine emits the right type at the right on-disk AST position.

**Outcome:** result. Re-derived every GT position from the actual generated
`main.py` AST. **6,352 annotations** across **1,253 files** had their
`(line, col)` corrected to AST truth; the AST-vs-GT position-mismatch count went
from **6,352 → 0**. No previously-correct annotation was changed (verified:
0 structural changes, 0 position collisions). The fix is applied **both** in the
generator (so future regenerations are correct) **and** as an idempotent
post-process over the committed corpus (so the shipped corpus is corrected now).

---

## 1. The bug

The autogen pipeline builds each `main.py` + `*_gt.json` from a micro-benchmark
template by substituting `<valueN>` placeholders. It copies `line_number` /
`col_offset` **verbatim from the template's `*_gt.json`** and never re-checks them
against the file it actually ships (`autogen/helpers.py::replace_placeholders_and_generate_json`
only substitutes *types*; positions pass through untouched).

Worked example named in the goal —
`assignments/starred_1_293_dict_tuple_float_str/`: the starred unpacking
`a, *b, c = func1, func2, func3, func4` is on **line 17** of the shipped
`main.py`, but `main_gt.json` places `a`/`b`/`c` on **line 18** and every later
binding `+1` (`d`@20, `e`@21, `f`@22, `g`@23 — `g` is past EOF). The function
defs (lines 2–15) are correct; only the trailing module-level block is shifted.
The benchmark adapter matches on line, so the engine's correctly-typed bindings
score `LOCATION_MISS` (and some neighbour-shifted ones score false `TYPE_MISS`).

## 2. Verified root cause

Not a `+1` quirk — the committed corpus is **stale relative to its templates**:

1. **Stale template positions.** Commit `7990076a` ("fixed inconsistencies
   between Python sources and ground truth files", 2025-10-09) corrected the
   `starred` **template** GT (`line 18 → 17`, `20 → 19`, …) — but the committed
   **corpus** (`autogen_typeevalpy_benchmark/`, last generated in `cede45d7`)
   was **never regenerated**, so it still carries the pre-fix positions. The
   generator faithfully propagated the old template's wrong positions.
   *(`git show 7990076a -- micro-benchmark-autogen-templates/.../starred/main_gt.json`
   shows exactly the `18→17` edits we see reversed in the corpus.)*

2. **Positions that cannot be inherited at all.** Some positions are
   **value-length-dependent** and therefore impossible to copy from a template:
   `functions/default` — `def my_func(x=<v1>, y=<v2>)` — the column of `y`
   depends on the rendered length of `x`'s default (`y` lands at col 19 / 21 / 24
   for `88` / `52.7` / `'qggfy'`). Likewise lambda parameter columns in
   `lambdas/chained_calls`. These **must** be re-derived from each generated file.

3. **Convention drift between corpus and templates.** The corpus was generated by
   an *older* template generation and uses naming/positions the current templates
   no longer use (corpus `A.B.a` attributes vs template `self.a`; corpus bare
   nested-function names `wrapper`/`inner` vs template `dec1.wrapper`/`outer.inner`;
   corpus single-line `def my_func(x=88, y=88)` vs template's multi-line form).
   This rules out "copy positions from the current template" — the only reliable
   source of truth is **the AST of the shipped `main.py` itself**.

**Why substitution doesn't move GT-referenced positions:** placeholders are
single-token, single-line, and always on the value (RHS) side, after every LHS
binding target / `def` / parameter the GT points at. So a template whose GT is
correct against *its* `main.py` yields a corpus whose GT is correct against the
generated `main.py` — and a template whose GT is stale yields a stale corpus.
The fix is to stop trusting inherited positions and re-derive from the AST.

## 3. The fix — where and how

Re-derive **every** GT `(line, col)` from the on-disk AST of the sibling
`main.py`, for all forms (not just the three named in the diagnosis).

* **Generator (future regenerations).** New module
  [`autogen/gt_positions.py`](../../autogen/gt_positions.py) is the canonical
  re-derivation core. `autogen/helpers.py::save_files` now calls
  `rederive_facts(code, ground_truth)` immediately before writing each
  `*_gt.json`, so positions come from the AST of the code just written rather
  than from the template. (Wrapped in `try/except SyntaxError` so error-case
  snippets that don't parse fall back to template positions.)

* **Committed corpus (corrected now).** The same core drives an idempotent
  post-process,
  [`experiments/autogen-gt-fix/rederive_gt_positions.py`](rederive_gt_positions.py),
  which audits or rewrites every `*_gt.json` in place. It was run over the whole
  corpus (`--fix`). Only `line_number`/`col_offset` are touched; types, names,
  structure, ordering and fact counts are untouched.

  > A full **regeneration** was deliberately *not* used: it would also rewrite
  > every `main.py` (different random values, multi-line `def` reformatting,
  > renamed case folders) producing a massive, hard-to-review diff that changes
  > the shipped sources. The in-place position post-process is surgical and
  > directly verifiable. The generator fix ensures correctness for any *future*
  > regeneration.

### Position convention (reproduced from the corpus; validated against templates)

1-indexed columns (`GT.col_offset == ast_node.col_offset + 1`):

| GT fact | AST anchor |
|---|---|
| `function` | the def **name** column; matched under bare / class-qualified / full-qualified spellings (the corpus is inconsistent) |
| `parameter` | the `arg` node, a body re-binding (`a += 93`), or — when dotted — a mislabeled `self` attribute |
| `function:"lambda" + variable` | the lambda's parameter `arg` |
| `variable` (plain) | the assignment-target `Name` (Store ctx), **scoped** by the fact's `function` qualifier |
| `variable` (subscript) | the explicit subscript target (`d["b"]=…`) if one exists, else the base binding (synthetic element facts copy the base) |
| `variable` (attribute / class var) | the `Attribute` target / class-body assignment, qualified by class path |

**Validation that the convention is right, not invented:** running the same
re-derivation against the **templates themselves** reproduces the template
authors' positions exactly — **0 mismatches over 794 matchable facts** (the 29
unmatched are template-only `self.x` / function-qualified-nested spellings the
corpus doesn't use). See [`audit_templates.json`](audit_templates.json).

The `assignments` total — **starred 5,400 + recursive_tuple 720 + augmented 7 =
6,127** — matches the prior diagnosis's *independent* AST scan exactly. The extra
**225** corrections are position bugs in other categories the diagnosis didn't
analyse (it focused on `assignments`); the task explicitly asked to re-derive
from the AST so it is correct for **all** forms, which surfaced these.

> Note on the "~4,400" figure: the diagnosis's 4,399 was the engine's
> `LOCATION_MISS` *subset*. The AST-vs-GT position-audit metric (6,352) is the
> *superset* of all position discrepancies — it also includes the ~1,080 starred
> facts that frame-shifted onto a neighbour and scored as false `TYPE_MISS`, plus
> the 225 in other categories. Both numbers are consistent; the audit catches
> every position error, not only the `LOCATION_MISS`-scoring ones.

### Worked example (independent AST cross-check; full table in [`validation_output.txt`](validation_output.txt))

`assignments/starred_1_293_dict_tuple_float_str` — every binding from the starred
assignment onward moves `−1` line; the four function defs are untouched:

```
  var a        OLD (18,1)  ->  NEW (17,1)   AST (17,1)  OK
  var c        OLD (18,8)  ->  NEW (17,8)   AST (17,8)  OK
  var d        OLD (20,1)  ->  NEW (19,1)   AST (19,1)  OK
  var g        OLD (23,1)  ->  NEW (22,1)   AST (22,1)  OK      (was past EOF)
  func func1   OLD ( 2,5)  ->  NEW ( 2,5)   AST ( 2,5)  OK      (unchanged)
```

`recursive_tuple_1_100…`: only `b` on the flat group `f, b = c, e = …` (line 37)
moves col `5 → 4`; all 30 other facts already correct and untouched.
`augmented_1_4_list`: only `b` (and its element facts) move line `11 → 10`; the
parameter facts at (5,11) and (6,5) untouched. **`NEW == AST` everywhere.**

## 5. Out-of-scope (558 unmatched, left untouched — NOT position bugs)

These reference a name that has no binding in the AST, so position cannot be
re-derived. **526/558 still land on a real AST anchor** (position already valid);
the other 32 are `exec`/`compile` cases where the variable is defined inside a
string literal and has no AST node at all (hand-authored convention).

| family | n | why unmatched |
|---|---:|---|
| `mro/two_parents_method_defined` | 480 | corpus **name+type corruption**: GT has `C` (the class) with `tuple` type + spurious subscripts where the template (fixed) has `c: ['C']`. Spurious facts a position-fix can't remove. |
| `decorators/nested_decorators` | 42 | GT names the function `dec` but the code has `dec1`/`dec2` (name mismatch; positions already correct). |
| `dynamic/compile`, `dynamic/exec` | 32 | variable defined inside a string (`"a = 93"`); no AST binding. |
| `args/multiple` | 4 | GT param `integers` vs code's `*arguments` (name mismatch; position already correct). |

These are **separate corpus-quality issues** (name/type corruption, dynamic
string code) orthogonal to the position bug. The **full regeneration** (§7) fixes
them holistically; the position post-process correctly leaves them alone.

## 6. Verification (no regression)

* **Idempotent:** re-running `--fix` changes 0 files.
* **Surgical diff:** across all 1,253 changed files, **only** `line_number`/
  `col_offset` changed — 0 facts added/removed, 0 type/name/variable/function/
  parameter field altered (`5,475` line changes, `1,620` col changes).
* **No collisions:** 0 distinct non-element facts map to the same new position
  (the signature of a disambiguation/scope bug — caught and fixed one such case
  in `assigned_self_call`, where a `function`-scoped `a` and a module `a` must
  not be swapped; the resolver is now scope-aware).
* **Templates unchanged & consistent:** template audit is 0-mismatch.
* **Generator wired & tested:** the real `save_files` path re-derives correct
  positions (including the value-length-dependent `functions/default` columns
  that template propagation cannot get right).

## 7. Required follow-on (NOT done here)

This corrects the *measurement* (a wrong GT), not the engine. To obtain the
corrected official autogen number, a **full autogen run against the engine**
(~77k facts scored) must be re-run on the corrected corpus — that is a separate
step and was intentionally **not** run here. A subsequent full regeneration of
the autogen corpus (with the now-fixed generator) is also advisable, as it would
additionally resolve the 558 out-of-scope name/type-corruption and dynamic
cases that a position-only post-process cannot.

## 8. Reproduce

```bash
# from the TypeEvalPy repo root (this worktree)

# audit the committed corpus (read-only): BEFORE the fix this reports 6,352
# mismatches; on the fixed corpus it reports 0.
python3 experiments/autogen-gt-fix/rederive_gt_positions.py autogen_typeevalpy_benchmark

# apply the fix in place (idempotent)
python3 experiments/autogen-gt-fix/rederive_gt_positions.py autogen_typeevalpy_benchmark --fix

# validate the convention against the templates (expect 0 mismatches)
python3 experiments/autogen-gt-fix/rederive_gt_positions.py micro-benchmark-autogen-templates

# worked-example BEFORE/AFTER table + corpus-wide before/after counts
python3 experiments/autogen-gt-fix/validate.py autogen_typeevalpy_benchmark \
    experiments/autogen-gt-fix/audit_before.json experiments/autogen-gt-fix/audit_after.json
```
